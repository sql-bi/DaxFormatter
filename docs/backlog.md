## Next
- B-1 The MCP server's workflows run on a supported Node.js LTS: `typescript-ci.yml` and `typescript-release-daxformatter-mcp.yml` set `node-version: "20"`, which reached end of life on 2026-04-30; on 2026-11-19 the LTS majors are 22, 24 and 26 ([release schedule](https://github.com/nodejs/Release#release-schedule)). Depends on B-1.

Done when `dotnet-release-dax-formatter.yml` fails right after it reads the version if the tag `Dax.Formatter-v<version>` exists, with a message that says to raise the version in `dotnet/version.json`.

## Open decisions
- B-20 Remove NBGV from the .NET toolchain? Since [ADR-0006](decisions/0006-write-the-dax-formatter-package-version-by-hand.md) it no longer computes the package version: it stamps the one in `dotnet/version.json`, adds the commit suffix outside `master` and puts the git height in the file version. The options: keep it, or set the version in the project file and change the release workflow, which reads the version from NBGV. The answer depends on whether the commit suffix and the file version are worth the tool, and on the scheme the MCP server takes (B-21).

## Known debt
- B-11 The REST contract is restated in each client: the .NET wire types in `dotnet/src/Dax.Formatter/Wire/`, the TypeScript port's types and serializer, and the zod schemas of the MCP tool. Cost: every contract change touches each copy. Repay with the OpenAPI contract and its shared test vectors (B-4).
- B-14 The MCP server says that `formatted` is null for invalid DAX, in the tool description in `typescript/packages/daxformatter-mcp/src/format-tool.ts` and in the comment of `formatted` in `src/daxformatter/types.ts`, while the service returns an empty string ([REST API, Response](design/rest-api.md#response)). Cost: an AI client that follows the tool description misses the empty string. Repay by fixing both texts, which raises the MCP server's version.
- B-15 Releases are tied to `master` only by the branch guard of the release workflows: a run uses the workflow file of the commit it runs on ([Workflows](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows)), so a branch whose copy drops the guard runs with the repository secrets, and the nuget.org Trusted Publishing policy names the workflow file, not a branch. Cost: whoever can push a branch and run workflows can publish from it. Repay: remove the nuget.org policy for `release.yml`, the .NET release workflow's name before the move in `6df1bf0`; run each release job in a GitHub environment that only `master` can deploy to, which holds the release secrets and which the nuget.org policy names ([Trusted Publishing](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing), [environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)).
- B-16 Some files under `dotnet/` don't follow `.editorconfig`: a missing or unwanted byte order mark, no final newline, trailing whitespace, and tabs, including in `Dax.Formatter.sln`, which Visual Studio writes with tabs. Cost: saving one in an editor that applies `.editorconfig` puts changes unrelated to the edit in the diff. Repay with one commit that only normalizes these files, and a `[*.sln]` section with `indent_style = tab`.
- B-22 The service rejects three kinds of valid DAX with a syntax error: a function without parameters, a function parameter with a default value and, sent as the expression of a model object, an expression with `=>` inside a string or a comment ([client API](design/client-api.md#limits-of-the-service)). Cost: no client can format them, and each returns the syntax error to its caller. Repay in the service, which is outside this repository; then remove the limits from `client-api.md`, `rest-api.md` and the .NET package readme, and update the live test that pins them.
